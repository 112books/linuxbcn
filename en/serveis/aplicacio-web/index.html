Web applications

When the site has to do things, not just explain them

Custom web applications to manage votes, members, hours or content. Free software, data on your own infrastructure.

When a website is not enough

A website informs. An application does. The difference shows when the work has to be done every week and depends on someone who knows how: member lists, votes, bookings, time tracking, registrations, inventories, permissions.

If the process exists and lives on paper, in a spreadsheet only one person understands or in a group chat, there is an application to be built.

What we build

  • Association and collective management: members, dues, registrations, self-publishing of content.
  • Votes and decisions: anonymous voting, automatic counting, minutes and history.
  • Contests and juries: entries, works, public voting limited to the room and jury voting.
  • Time and jobs: hours per project, reports, invoicing from hours.
  • Content and publishing: platforms to publish with permissions and simple workflows.

When we do not build it

  • If a free tool already exists that does the job and can be adapted, we use it.
  • If the problem is communication, not software, we say so.
  • If the decision is to automate a process nobody has defined yet, we define it first.

How we do it

1. Understand the real process

We watch how the work is done now, on paper, in spreadsheets or in chat. The application must reproduce the process that works, not the one we wish existed.

2. Define the minimum version

We pick the function that saves the most work and leave the rest for later. A small tool people use is worth more than a large system nobody adopts.

3. Build and test

We code with free technologies and test with the people who will use it, with real day-to-day data.

4. Measure and grow

After a few weeks we look at what is used and what is not. What is not used is removed; what is missing is added with judgement.

Decisions we make by default

  • No third-party accounts: no registration anywhere is needed to use the application.
  • Minimised data: only what the function needs is collected. If a vote can be anonymous, it is.
  • Accessibility: it can be used with a keyboard and a screen reader.
  • Export: the data is yours and can be exported in an open format.

If the problem is that WordPress has outgrown you, before coding anything see how we move a WordPress site to static.

One example

With Taro Photo App, a photography association manages members, contests and content publishing on its own system, with in-room voting and without depending on any closed platform. It is free software: if one day they want another provider, the code goes with them.

Frequently asked questions

Is a spreadsheet or a cloud tool not enough?

Often it is, and that is the first thing we check. If a shared spreadsheet, a form or an existing tool solves the problem, we will not sell you an application. We build when the tool does not exist, when data must not leave your infrastructure or when the process is specific enough that no generic product fits.

Where does the data live?

On the server we decide with you. It does not go through third-party services that can exploit it, and no external account is needed to use it.

Who can use it and who maintains it?

The people you choose, with role-based permissions where needed. The code is free when it is our own tool, and the documentation stays in your hands.

How long does it take?

It depends on whether there is a single function or a system with roles, history and exports. We start with the minimum version that solves the problem and grow from real use.

What if we later want a mobile app?

First we ask whether it is needed. A web application that works well on a phone is often enough and updates itself; a native app is different work and different maintenance.

Let’s talk about the process you want to solve

Tell us how the work is done today. If an existing tool is enough, we will tell you before quoting anything.
